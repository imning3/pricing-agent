# 建设方案类文档拆分规则

## 字段语义（先记住）

- **subsystem（子系统）**：moduleSystem 字段。系统下按业务域划分的大块。
- **sw（软件）**：moduleConfig 字段。子系统下开发的软件产品/配置项。
- 软件内部的功能组成、工作流程等不再细分层级——功能块（softwareObject）由后续抽取阶段按条目判断，本阶段不输出。

## 层级形态学（通用判定原则）

1. 此类文档通常呈多层结构：**系统级（全文）→ 分系统/子系统级 → 软件级 → 软件内部（功能组成/工作流程/性能/接口等叙述）**。不同方案的章节编排差异很大，
   **判层级看叙述内容与命名特征，不看固定章节位置**。
2. **子系统层特征**（满足其一即可）：
   - 标题或正文含"XX子系统""XX分系统"命名；
   - 功能及性能要求、系统组成、总体设计、详细设计类章节下，按业务域分组的一层，其下还有更细的软件/组件叙述。
3. **软件层特征**：标题以"XX软件""XX平台""XX系统（较小粒度）""XX模块/工具"结尾的可交付组件；一个子系统通常含若干软件。叫法混杂（软件/平台/模块混称）时按"是否可独立交付的软件产品"归一判断，用其正式全称。
4. **同一软件的描述常分散多章**：功能要求处一处、详细设计处另一处、组成描述又一处。凡叙述同一软件的章节给**相同 (sub, sw) 坐标**，由代码拼接正文。
5. 层级断裂、伪标题、编号缺失等结构异常：按标题语义与上下文就近归组，不要因结构紊乱而放弃或机械按层级数字归组。

## role 判定（每章节三选一）

- **functional**：功能需求/功能及性能要求类叙述（"应提供/应支持/具备XX功能"）；
- **design**：详细设计/系统组成/工作流程/接口设计类叙述；
- **skip**：非功能内容——概述、依据文件、技术体制/标准规范、项目管理、进度计划、保障方案、风险分析、配套清单、结论，以及一切与具体软件功能无关的章节。skip 章节的深层小节一并跳过（不要把管理性大章下的内容归到任何软件）。

## 纪律

- sub/sw 必须用**文档原词**；跨章同物同名（同一软件在两处叫法不同时用其正式全称）；
- 拿不准某章属于哪个软件时：若明显是功能/设计内容但归属不明，宁 skip 不编造坐标；
- 不依据项目名、文件名推断坐标，只依据章节内容本身。
